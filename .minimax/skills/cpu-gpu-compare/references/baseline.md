# 已测基线与解读陷阱

基线机器：AMD Radeon Pro VII（Vega 20 / gfx906），Windows，torch-directml 0.2.5.dev240914。
CPU：Intel Xeon E5-1650 v4 @ 3.60 GHz，12 逻辑核。
配置：YOLOv8s @ 512px / batch 8 / workers=0 / mosaic=0 / fliplr=0 / scale=0.3 / hsv_s=0.4 /
seed=0 / amp=False / device=privateuseone:0。

> **读这张表之前先看 §6 证据台账。**
> 本文件里的每个数字都标了证据等级。1.x 版本里有些数字是「抄下来就信」的，
> 实测发现其中几处**无法复现**（见 §6），所以现在必须先看台账再引用。

## 1. CPU 与 A 卡对比（当前版本实测）

| 环节 | CPU | A 卡（DirectML） | 对比 |
| --- | --- | --- | --- |
| 损失前向（真实训练循环，中位数） | 55.2 ms | 96.3 ms | CPU 快 1.74× |
| 损失反向 | 11.5 ms | 23.6 ms | CPU 快 2.05× |
| 模型前向 | 1202.8 ms | 63.1 ms | **A 卡快 19.1×** |
| 模型反向 | 1831.0 ms | 145.8 ms | **A 卡快 12.6×** |
| 一个 iteration（真实训练循环，中位数） | 2671.5 ms | 323.1 ms | **A 卡快 8.27×** |
| 整轮训练（每轮墙钟） | 52.81 s | 12.65 s | **A 卡快 4.17×** |
| 25 轮总耗时 | 1320 s（投影，实测 5 轮） | 316.3 s（实测） | **A 卡快 4.17×** |
| 最终 mAP50 | 0.84309（**只到 5 轮**） | **0.99463**（25 轮） | |
| 最终 mAP50-95 | 0.6963（**只到 5 轮**） | **0.96404**（25 轮） | |
| 损失计算在哪算 | CPU（整段在 CPU） | `privateuseone:0`（整段在显卡） | |
| 训练步里回落到 CPU 的算子数 | 1639 / 1644 | **20 / 2052（0.97%）** | |

**一句话结论**：端到端 4 倍多的加速几乎全部来自模型前向/反向（卷积这种大张量），
不是损失。**A 卡把损失的比例从 CPU 上的 2% 顶到了 30%** —— 这才是 A 卡上真正的瓶颈，
也是补丁 12 要管的那块。

**旧版本这张表写过「A 卡快 6.3~6.7×」，用的是 nc=2 的配置**（模型头更大、损失更重）。
当前数据集是 nc=1，模型头更小，所以倍数从 6.x 变成 4.2x。两组数字各自成立，
但**不能混着引用** —— 引用时必须写清 nc。

## 2. 补丁 12（高级索引 → 展平 gather）的 A/B

干净机器上同机同时段配对跑（25 轮，只差 `flat_index` 一个开关）：

| 配对 | 补丁 12 开 | 补丁 12 关（原生 `aten::index`） | 提升 |
| --- | --- | --- | --- |
| 本轮（nc=1，干净） | **316.335 s**（12.65 s/轮） | **355.159 s**（14.21 s/轮） | **10.9%** |
| 历史配对 A | 287.722 s（11.51 s/轮） | 312.467 s（12.50 s/轮） | 7.9% |
| 历史配对 B | 305.874 s（12.23 s/轮） | 319.474 s（12.78 s/轮） | 4.3% |

**收益幅度在 4% ~ 11% 之间浮动**，取决于代码版本与机器负载。
所以报结论要写「4~11%」这个区间，不要挑一个好看的数字。

两次训练的最终指标**逐位相同**（本轮 mAP50 0.99463 / mAP50-95 0.96404），
历史四次也逐位相同（mAP50 0.99475 / mAP50-95 0.9855）——
改写只换算法路径，不改数值语义。

**组件级怎么看到的**：补丁的收益 100% 在损失前向，**145.0 ms → 96.3 ms（快 1.50×）**；
模型前向/反向它一个算子都没改（直方图 331 vs 331）。

**为什么组件收益比端到端大**：补丁每次损失前向多出 ~200 个小算子
（偏移折算、负下标归一、形状算术）和 16 次 `_local_scalar_dense`（D2H 标量回读 = 越界检查）。
DirectML 每个算子有 ~0.2~3 ms 固定开销，D2H 回读还会打断流水线。
所以**补丁的收益正比于「原生 `aten::index` 的元素数 ÷ 补丁固定开销」**：
索引张量小的时候补丁反而更慢（合成 batch 上是 −13%）。
换更大的 batch、更多目标框、更大的模型，收益才会更明显。

## 3. 算子级证据：补丁到底改了什么

同一次训练步里的 aten 算子直方图（补丁开 / 关）：

| 阶段 | 补丁 12 开 | 补丁 12 关 | 差 |
| --- | --- | --- | --- |
| 模型前向合计 | 331 | 331 | **0** |
| 损失前向合计 | 659 | 458 | +201 |
| 损失前向 `index` | 1 | **13** | **−12** |
| 损失前向 `gather` | **14** | 2 | +12 |
| 损失前向 `_local_scalar_dense` | 20 | 4 | +16 |
| 反向 `index_put_` | 2 | 0 | +2 |

读法：补丁把损失前向里的 **13 个 `aten::index` 中的 12 个**改写成 12 次 `gather`；
模型前向完全没被碰，所以模型侧的加速是显卡本身的功劳。
代价是每次损失前向多 ~200 个小算子和 16 次 D2H 回读。

**注意版本差异**：旧版本文档写「ultralytics 的检测损失里正好有 9 处这样的高级索引」、
「`aten::index` 占前向 60% 以上 CPU 时间」。在 **ultralytics 8.4.213** 上实测是
损失前向里 `aten::index` 只调用 13 次 —— 旧结论不成立，别再照抄。

## 4. 陷阱一：队列状态会放大差距（**口径必须写清**）

同一个损失前向，「队列状态」有两种以上口径，**不同口径能得出相反的结论**。
本仓库用下面三个名字统一称呼，引用时必须带口径名：

| 口径名 | 定义 | 实测（原生 `aten::index`） | 实测（展平 `gather`） |
| --- | --- | --- | --- |
| **B1 排空** | 每次计时前做一次标量回读，把 DirectML 命令队列排空 | 48.7 ~ 55.0 ms | 51.6 ~ 54.0 ms |
| **B2 半满** | 先跑一次模型前向（**不**排空）再进损失 —— 真实训练的状态 | 55.0 ms | 57.8 ms |
| **B3 积压** | 连续反复算同一个损失，中间**没有任何 CPU 工作** | 175 ms | 53 ms |

**B3 才是旧文档里「快 3.3 倍」的来源。但 B3 是个陷阱状态**：
DirectML 的命令队列在这种状态下可能直接卡死，下一次前向的第一个算子永远不返回。
实测复现 B3 时经常拿不到数（要配看门狗），而且**复现出来的口径和别的口径不可比**。

所以正确的说法是：

- 在 **B1/B2（可复现的状态）** 下，补丁在损失前向上**并不更快**（甚至慢 5~10%）；
- 在 **B3（容易卡死的状态）** 下补丁快 3.3×，但这个状态不可靠；
- 真实训练队列处于 B1 与 B2 之间，所以**可信的量级只有端到端的 4~11%**。

> 1.x 版本的文档只写「队列空 / 队列积压」两栏而没定义口径，
> 结果两个执行者得出相反结论（一个测到补丁慢 10%，一个测到快 3.3×）。
> **报结论时必须同时给两栏，并且写明是 B1 / B2 / B3 哪一档。**

## 5. 陷阱二：组件收益 ≫ 端到端收益

512px / batch8：A 卡一个 iteration 323 ms 里，模型前向 63 ms + 模型反向 146 ms，
损失前向 96 ms。补丁把损失前向压掉 48.7 ms，占单步 15%，折算到整轮就是 10.9%。
**组件上快 1.50×，端到端只有 10.9%**，写 README 时别把组件数字当端到端数字。

另外：**组件级五项不可相加**。用合成分项测出来的
（模型前向 63 + 模型反向 146 + 损失前向 96 = 305 ms）和实测 iteration（323 ms）
勉强自洽，但换 batch 配置后就不再自洽。做「瓶颈占比」推断要用实测 iteration。

## 6. 陷阱三：同配置两次实测能差 6%

`flat_index=True` 两次实测：305.9 s 与 287.7 s（差 6%）。
所以任何小于 ~6% 的端到端差异都不可信 —— 要配对跑，而且至少两对。

## 8. 复现命令

```powershell
$env:PYTHONPATH='<repo>\_debug\envs\yolo_dml_env;<repo>\_debug\envs\yolo_train_env'
Set-Location '<repo>'
$py = 'C:\Users\<user>\anaconda3\envs\maimai\python.exe'

# 数值对齐
& $py -u -m pytest tests/ -q
& $py -u -m Direct_AMD_train doctor

# 组件级（两个进程，合成 batch）
& $py -u .minimax\skills\cpu-gpu-compare\scripts\bench_components.py cpu
& $py -u .minimax\skills\cpu-gpu-compare\scripts\bench_components.py dml

# 真实训练循环逐步计时（更接近真实）
& $py -u .minimax\skills\cpu-gpu-compare\scripts\bench_step.py dml_flat 3
& $py -u .minimax\skills\cpu-gpu-compare\scripts\bench_step.py dml_noflat 3
& $py -u .minimax\skills\cpu-gpu-compare\scripts\bench_step.py cpu 2

# 算子直方图差分（补丁到底改了什么）
& $py -u .minimax\skills\cpu-gpu-compare\scripts\bench_opdiff.py dml_flat
& $py -u .minimax\skills\cpu-gpu-compare\scripts\bench_opdiff.py dml_noflat

# 端到端配对（自带超时保护）
& $py -u .minimax\skills\cpu-gpu-compare\scripts\bench_ab.py --epochs 25 --timeout 1800

# 数值对齐细查（补丁开/关逐位相同）
& $py -u .minimax\skills\cpu-gpu-compare\scripts\bench_align.py
```

训练产物在 `_debug/runs/<name>/results.csv`，`time` 列是累计秒数，
最后一行是总耗时，每轮耗时 = 相邻两行相减。
